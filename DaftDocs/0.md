# PC Buildmate 设计文档（粗略版 v0.1）

## 0. 文档定位

- 读者：Android Studio LLM、测试生成器、少量人工闸门。
- 性质：可执行契约 + 自动验收协议 + 变更控制规则，不是产品说明书。
- 原则：行为等价、契约等价；实现结构不限；范围外硬阻塞。
- 命名统一：**PC Buildmate**；代码包名 `pcbuildmate`。

## 1. 范围

**首版做：** 静态目录、六功能端到端、MVI 三层、诊断/替换两张状态机、CNY 参考价带日期、中文 UI、离线可用。

**首版不做（硬阻塞）：** FPS/跑分预测、3D 装配、实时库存、二手价、目录版本对比、相机/AR、推送、后台自动刷新、网络实时价格、账号系统。

**主用户：** 首次装机者、预算有限的升级用户。发烧友/小店为次要场景，不进首版验收任务。

## 2. 术语与状态

- `BuildRevision`：一次配置快照，id 单调递增；编辑、Undo、Apply 都生成新 revision。
- `VerificationState`：`VERIFIED / REPORTED / EMPTY`，字段级证据。
- `RuleOutcome`：`PASSED / CONFLICT / UNVERIFIED`，规则级结果；继承输入字段最弱证据。
- `Stale`：派生属性，`diagnosis.revision != currentRevision`，不是独立状态。
- `CatalogueVersion` / `PriceDate`：静态目录版本和参考价日期。

**不可违反的语义：**
- 缺字段不得 PASS，只能 UNVERIFIED。
- 来源冲突不新增枚举，返回 UNVERIFIED + `reason=SOURCE_CONFLICT`。
- 旧诊断不得覆盖新 revision。
- Apply 前 baseRevision 必须等于当前 revision；Apply 后必须全量重检。
- 无候选不得静默超预算或放宽硬约束。

## 3. 核心契约（只读，LLM 只能实现不能改签名）

```kotlin
data class BuildRevision(
    val id: Long,
    val buildId: String,
    val items: List<BuildItem>,
    val totalCny: Long,
    val catalogueVersion: String,
    val priceDate: String,
    val userModified: Boolean
)

data class BuildItem(
    val componentId: String,
    val category: Category,
    val quantity: Int,
    val unitPriceCny: Long
)

data class CatalogueRecord(
    val componentId: String,
    val category: Category,
    val manufacturer: String,
    val model: String,
    val partNumber: String,
    val attributes: Map<String, FieldValue>,
    val priceCny: Long,
    val priceDate: String,
    val catalogueVersion: String,
    val isDemo: Boolean
)

data class FieldValue(
    val value: Any?,
    val state: VerificationState,
    val source: String?
)

sealed interface RuleOutcome {
    data class Passed(val ruleId: String, val weakest: VerificationState) : RuleOutcome
    data class Conflict(val ruleId: String, val left: FieldRef, val right: FieldRef, val severity: Severity, val weakest: VerificationState) : RuleOutcome
    data class Unverified(val ruleId: String, val missingField: String?, val reason: UnverifiedReason, val weakest: VerificationState) : RuleOutcome
}

data class SuggestionResult(
    val baseRevision: Long,
    val conflictId: String,
    val candidates: List<Candidate>,
    val noCandidate: NoCandidateReason?
)

data class Candidate(
    val componentId: String,
    val priceDeltaCny: Long,
    val specDelta: Map<String, String>,
    val affectsOtherRules: List<String>
)

data class NoCandidateReason(
    val blockingConstraint: String,
    val suggestedDirection: String // 加预算/换类别/放宽偏好，不承诺全局最小变更
)
```

`Category`、`Severity`、`UnverifiedReason` 用枚举，值在 `contracts/` 中冻结。

## 4. 规则表

规则以数据/DSL 表达，每条含：

| 字段 | 说明 |
|---|---|
| `ruleId` | 如 `CPU_SOCKET_MATCH` |
| `inputs` | 字段路径列表 |
| `comparator` | 相等/包含/数值比较/集合包含 |
| `onMissing` | 固定返回 `UNVERIFIED` |
| `severity` | BLOCKER / MAJOR / MINOR |
| `fixtures` | pass/conflict/unverified/缺字段四类用例 |

首版规则 10–15 条，覆盖：CPU 插槽、芯片组/BIOS、内存代际、内存容量/插槽、GPU 长度/厚度、PSU 连续功率/接口、散热器高度/扣具、主板板型、机箱存储/扩展位。

新增硬件代际：扩数据 + 加 fixture，不改 UI。

## 5. 状态机

### 5.1 诊断

```
Idle → Running(revision) → Done(revision) / Failed(revision, reason)
```

- `Stale` 派生，不设状态。
- Running 中重复触发：忽略，保留当前 Running。
- 编辑产生新 revision：旧 Done 自动 stale；不自动重跑。
- 失败可重试，回 Idle 再 Running。

### 5.2 替换

```
Idle → Candidates(baseRevision, conflictId)
     → Previewing(baseRevision, candidateId)
     → Rechecking(previewRevision)
     → Applied(newRevision) / Rejected / NoCandidate
```

- 任何 build 编辑使 Candidates/Previewing 失效，回 Idle 并触发重新诊断。
- Preview 只读，不写回 build。
- Apply 前校验 baseRevision；不等则 Rejected。
- Apply 后允许继续编辑，用 revision 保护结果。
- 非法事件统一 `Rejected(reason)`，状态不变。

### 5.3 导航 guard（不做 FSM）

- 无 build 不进诊断。
- 少于两个 saved build 不进比较。
- 编辑中离开 Workspace 自动存草稿，不阻断。

## 6. 六功能模块契约

每个模块给 LLM 的卡片包含：输入、输出、失败模式、禁止事项、验收用例。

1. **硬件数据库**：输入查询/ID；输出 `CatalogueRecord`；禁止编造字段；缺字段标 EMPTY。
2. **DIY 工作区**：输入编辑 Intent；输出新 `BuildRevision`；总价立即重算；禁止 UI 直接算规则。
3. **兼容性检查**：输入 `BuildRevision` + catalogue；输出 `List<RuleOutcome>`；禁止缺字段 PASS。
4. **预算推荐**：输入预算/用途/偏好；输出可编辑 build；不承诺全局最优；不可行必须报告。
5. **替换建议**：输入冲突 + build；输出 `SuggestionResult`；先过滤硬约束再排序；无候选结构化返回。
6. **构建比较**：输入 2–3 个 saved build；输出 delta；诊断过期显示“请重新检查”，不显示旧绿；首版不做 performance band。

## 7. 治理规则

- **契约变更**：走 git，默认批准自动合并；保留 diff、影响模块、ADR；CI 记录不阻塞。
- **测试批次**：自动跑、自动归因五类（规格/oracle、LLM 断言、fixture、domain、UI/state）；未分类进人；批次最终通过由人批准。
- **范围外**：硬阻塞三层——依赖检查、关键词/符号检查、功能开关；解除必须提范围变更文档，人批准。

## 8. 测试策略

- 规则表回归：每条规则 pass/conflict/unverified/缺字段。
- 属性测试：总价、revision 单调、weakest evidence、Undo 恢复、比较 delta。
- ViewModel：快速编辑 + 延迟诊断 + 旧结果丢弃。
- Compose semantics：可见、可点、滚动、返回、小屏；只断言 key 和状态，不断言自然语言全文。
- 模型驱动随机测试：从状态机转移表生成合法序列；非法事件断言“状态不变 + Rejected”。
- LLM 意图测试：LLM 输出 `IntentSpec` → planner 转操作 → 逐步 postcondition；LLM 断言只做候选，不直接判 bug。
- Mutation testing：关键 mutation 必须被杀（`unverified→pass`、`>=→>`、旧 revision 覆盖新 revision），作为合并闸门。
- 静态数据：JSON schema + 外键/单位/日期/证据状态/demo 标记校验。

每个模块 prompt 必须带六块：目标、输入契约、输出契约、禁止事项、验收用例、失败模式。生成顺序：数据层 → 规则引擎 → 替换排序 → ViewModel → UI。每步编译 + 跑契约测试，不过不进入下一步。
